# План решения

План разработки решения задачи матчинга товаров E-CUP 2026. Составлен на основе ТЗ ([README](../README.md)) и фактически доступных файлов ([ASSETS](ASSETS.md)).

## Целевые показатели

- **Метрика:** Macro Averaged PR-AUC (`sklearn.metrics.average_precision_score`), усреднённая по 20 категориям.
- **Ограничения по времени (жёсткие):** Check — 1 мин, Public — 6 мин, Private — 13 мин.
- **Ресурсы:** 20 ядер CPU, 200GB RAM, 1× NVidia H100 (80GB).
- **Приоритет:** скорость исполнения имеет вес, сопоставимый с местом на лидерборде.

## Формат запуска (строго как в решении-примере)

- Точка входа — `run.py` в корне сабмита, вся логика вынесена в `src/`.
- `metadata.json`:
  ```json
  {
      "image": "odsai/ecup26-matching-baseline:1.0",
      "entry_point": "python -u run.py"
  }
  ```
- Аргументы командной строки (как в `examples/matching-baseline-lightweight/run.py`):
  - `--items_path` — parquet с товарами;
  - `--matches_path` — parquet с парами;
  - `--output_path` — путь для итогового `.csv`.
- Выход — `.csv` со столбцами `id1`, `id2`, `predict` (допускаются «сырые» скоры).

## Доступные данные и их ограничения

Используем **только то, что уже есть в `assets/`** (см. [ASSETS](ASSETS.md)):

| Файл | Статус | Использование |
|------|--------|---------------|
| `assets/matches.parquet` (4.1MB) | ✅ есть | ручная разметка, `target ∈ {0,1}` — основной обучающий сигнал |
| `assets/matches_llm.parquet` (104.7MB) | ✅ есть | LLM-разметка, `target ∈ [0,1]` — доп. сигнал |
| `assets/items_human.parquet` (214.2MB) | ✅ есть | тексты товаров из ручной разметки |
| `assets/items.parquet` (4.1GB) | ❌ **не скачан, в репо отсутствует** | полный корпус товаров — недоступен |

**Ключевое следствие отсутствия `items.parquet`:**
- Полный текст товара доступен только для товаров из `items_human.parquet`.
- Пары из `matches_llm.parquet`, ссылающиеся на товары вне `items_human.parquet`, не смогут получить текст и будут отброшены при построении пар (как в `_build_pairs`).
- Поэтому обучение опирается прежде всего на `matches.parquet` + `items_human.parquet`; из `matches_llm.parquet` используем только пересечение по `id`, оба конца которых есть в `items_human.parquet`.
- Расширение обучающей выборки за счёт полного корпуса возможно только после скачивания `items.parquet` (вне текущего скоупа).

## Этапы работы

### 1. Данные (`src/data.py`)
- Чтение parquet, сборка текстового представления товара из `name` + `category` + развёрнутых `attributes` (json).
- Построение пар `(text1, text2)` по `id1`/`id2` через словарь `id → text`; пропуск пар с отсутствующими текстами.
- Разделение train/valid **со стратификацией по `category`** (метрика считается по категориям — валидация должна это отражать).

### 2. Признаки (`src/features.py`)
- Базовый подход: эмбеддинги CLS-токена cross-encoder (как в baseline) → классификатор.
- Оптимизации инференса под лимиты времени: bf16 на H100, `sdpa`-attention, батчинг, бакетинг по длине, предаллокация массива результатов, отказ от `np.vstack`.
- Резервные/альтернативные признаки для скорости: лексические (пересечение токенов, длины, числовые атрибуты) — дёшевы и помогают быстрым категориям.

### 3. Модель (`src/model.py`, `src/pipeline.py`)
- Классификатор поверх эмбеддингов (логрег/градиентный бустинг) — быстрый инференс, `predict_proba`.
- `train_pipeline`: обучение на доступных данных, сохранение весов (joblib/чекпоинт) в артефакты сабмита.
- `predict_pipeline`: загрузка данных → признаки → скоринг → сохранение `id1,id2,predict` в CSV (порядок пар сохраняется).

### 4. Валидация
- Локальная эмуляция запуска на `items_human.parquet` + `matches.parquet`, как рекомендовано в ТЗ.
- Метрика: macro PR-AUC через `average_precision_score` по категориям (не `auc` по PR-кривой — завышает результат).
- Контроль времени: замер полного прохода и экстраполяция на объём Public/Private.

### 5. Бюджет времени и упаковка
- Профилирование инференса, подбор `batch_size`, `max_seq_length`, dtype под лимиты 6/13 мин.
- Все веса и артефакты — внутри архива/образа (интернета при запуске нет).
- Контроль лимитов: архив ≤ 5GB, образ ≤ 15GB.

## Риски

- **Нет полного `items.parquet`** → урезанный объём обучения и невозможность оценить покрытие текстами на тестовом распределении. Основной риск качества.
- **Жёсткие лимиты времени** → тяжёлый cross-encoder может не уложиться в Private (13 мин); нужен запас по скорости или более лёгкая модель.
- **Дисбаланс и разное качество разметки** (ручная vs LLM) → аккуратно взвешивать источники.
- **Разное распределение категорий** на тесте → стратифицированная валидация и macro-усреднение обязательны.
