# Правила

Свод правил проекта: ограничения соревнования из ТЗ ([README](../README.md)) и договорённости по организации репозитория. Нарушение правил соревнования ведёт к дисквалификации решения; нарушение правил репозитория ломает воспроизводимость и запуск.

## Правила репозитория

- **Код — только в `src/`.** Вся логика решения живёт в `src/`; в корне лежит лишь тонкий `run.py` (entry point) и `metadata.json`.
- **Запуск — строго как в решении-примере.** Точка входа `python -u run.py`, аргументы `--items_path`, `--matches_path`, `--output_path`. Не менять интерфейс запуска.
- **Вся документация — в `docs/`.** Исключение: `README.md` остаётся в корне.
- **`README.md` — в корне репозитория.**
- **`assets/` не трогаем.** Используем только те файлы, что уже есть локально. Файлы не переименовываем, не перезаписываем, не докачиваем в рамках задач по репозиторию.
- **`examples/` не трогаем.** Baseline от организаторов — только для чтения и справки.
- **Полный `items.parquet` доступен только для обучения.** Файл находится локально в
  `assets/`, не входит в сабмит и не должен читаться production-пайплайном. Архив
  `matching-baseline-submit` по-прежнему отсутствует (см. [ASSETS](ASSETS.md)).
- **Каждой входной паре — предсказание.** Строки пар никогда не отбрасываются; при отсутствии текста товара скор = 0 (иначе провал Result-стадии).
- **Рантайм-зависимости — в пределах baseline-образа.** Не добавлять тяжёлые новые зависимости в рантайм без проверки, что они есть в образе (интернета при запуске нет).
- **Локальная разработка — через `.venv`** (в `.gitignore`). Прогресс фиксируем в [PROGRESS](PROGRESS.md).

## Правила соревнования (из ТЗ)

### Формат решения
- Контейнерное соревнование: обучить модель → собрать Docker-контейнер с кодом и весами → отправить архив → автономный запуск на закрытых данных.
- В архиве обязателен `metadata.json` с `image` и `entry_point`.
- Все необходимые файлы модели должны быть внутри архива и/или образа.

### Формат ввода/вывода
- Вход: `--items_path` (товары), `--matches_path` (пары), `--output_path` (результат).
- Выход: `.csv` со столбцами `id1`, `id2`, `predict` (допускаются «сырые» скоры).
- **Каждой** тестовой паре должен соответствовать результат — пропуски недопустимы (иначе Result-стадия завершится ошибкой).

### Среда исполнения
- **Запуск без доступа в интернет** — все библиотеки, модели и артефакты уже должны быть в образе/архиве.
- Тестовые данные полностью закрыты, содержат другие товары; в товарах теста только те, что участвуют в парах.
- Проверка в 3 стадии: Docker → Result → подсчёт метрики. Падение на любом наборе завершает проверку.

### Метрика
- Macro Averaged PR-AUC: PR-AUC по каждой из 20 категорий, затем усреднение.
- Использовать `sklearn.metrics.average_precision_score`. **Нельзя** считать через `auc` по PR-кривой — завышает результат из-за интерполяции.
- Соотношение public/private ≈ 30/70.

### Ресурсы и лимиты времени
- 20 ядер CPU, 200GB RAM, 1× NVidia H100 (80GB).
- Время: Check — 1 мин, Public — 6 мин, Private — 13 мин. Превышение = провал стадии.

### Лимиты размеров и команды
- Архив с решением: ≤ 5GB.
- Docker-образ (в архиве): ≤ 15GB.
- Решений в день: ≤ 5. Участников в команде: ≤ 5. Финальных решений: 2.

### Переразметка данных через LLM
- Разрешена **только с моделями с открытой лицензией**. Проприетарные LLM запрещены.
- Код обучения модели и разметки должен быть **воспроизводимым**.

### Оценка финалистов
- Топ-15 private-лидерборда проходят дальше; жюри запрашивает исходные репозитории.
- Оцениваются качество работы с данными/моделями, ресурсоёмкость, изящность и новизна подходов.
- **Скорость работы решения — высокий приоритет**, сопоставимый с местом на лидерборде.
